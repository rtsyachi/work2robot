# デモ入力素材の方針（正本）

**状態：方針と制作計画。素材はまだ存在しない。** 提出動画全体の構成は `docs/DEMO.md`、データ構造は `docs/WORKFLOW_SPEC.md` を参照。

## 2種類の映像を区別する

| 種類 | 用途 | アプリで解析するか |
|---|---|---|
| **導入用の実写素材** | 提出動画の冒頭で物流現場の雰囲気を伝える | **しない**（背景説明用） |
| **デモ用の模擬作業動画** | アプリに入力し、作業・判断を抽出させる | **する** |

## 確定事項

- 導入用の実写素材は、無料で利用可能な既存素材を短く使う。使用前に利用条件を確認し、確認日・出典・条件を記録する。
- アプリの入力動画は**デモ用に生成した模擬作業動画**とする。ユーザーによる現場撮影は必須タスク・開発の前提にしない。
- 入力動画であることと**生成・模擬素材であること**を、アプリ画面と提出動画で明示する。
- 硬い箱、ソフトバッグ、壊れ物を含める。
- 「大きい箱」の定義（**底面積0.15㎡以上**）を、説明テキストに最初から含める。Claudeが閾値を生成したように見せない。
- 基準を示さない条件（「重い荷物」）を1つ含め、確認事項として保持され、確定した分岐として実行されないことを示す。
- Claudeとのリアルタイムな質疑応答はMVPに含めない。
- 見た目で確定できない属性（重量、壊れ物の中身など）は、ラベル・説明・模擬荷物マスタで根拠を与える。
- **積付先はカゴ車**とする。入力動画・模擬荷物マスタ・ワークフロー・シミュレーションの設定をカゴ車で揃える。
- **壊れ物（荷物D）は、ロボットが押し込まずに上段へ置く経路**とする。属性不明のときだけ人へ引き継ぐ。
- **説明はテキストで入力する**（提供された説明テキスト）。音声の録音・合成はアプリ入力に使わない。
- **ワークフロー抽出モジュールの入力はテキスト**とする。最初は固定テキストで開発し、後で動画を観測テキストへ変換する機能を作る（モジュール分担は `docs/ARCHITECTURE.md`）。
- 入力素材が生成物でも、次は**実際のアプリ処理**として実行する：動画からの観測可能な動作・状態変化の抽出、説明との統合、曖昧な条件・不足情報の確認事項への整理、ワークフロー生成、確定条件を反映した実行・シミュレーション。

## 入力動画の要件

1. 荷物と積付先が同じ画面に映り、置く前・途中・後の状態を追える。
2. 荷物の数・形・大きさ・位置が途中で不自然に変化しない。
3. 作業者の身体で積付先が長く隠れない。**固定カメラ・斜め上からの構図**を基本候補とする。
4. カゴ車の開口部と内部（下段・上段）が斜め上から見え、どこに置いたか判別できる。
5. 見た目で確定できない属性には、ラベル・説明・模擬荷物マスタのいずれかで根拠がある。

## 台本・正解データと入力の分離

- 動画生成用の台本・シーン定義・正解データは**評価用**であり、アプリの入力経路から読まない。動画解析結果の代わりに流し込まない。
- アプリへ渡すのは「入力動画」「説明テキスト」「模擬荷物マスタ」だけ。評価用データとは別ファイル・別ディレクトリで管理する。
- 動画→観測テキストの変換ができるまでの**開発用の固定観測テキスト**は、根拠を`provided_text`として扱い、`video_observation`として表示しない。提出動画の実演では、変換機能が動画から出した観測テキストを使う。
- 模擬荷物マスタには、動画から観測すべき情報（置く順番・位置など）を含めない。
- 説明の台本文字列を直接入力する場合は**「提供された説明テキスト」**として表示し、音声認識結果のように見せない。
- 模擬動画での成功を、実写動画での認識性能や実機の動作保証として説明しない。

## 生成方式の比較（提案）

| 観点 | 動画生成AI | プログラムによる3D生成 |
|---|---|---|
| 期間内の実現性 | 1カットは早いが、要件を満たすまで再生成を繰り返す可能性が高い | 初期構築に1日程度。以後の修正は速い |
| 制御しやすさ | 荷物の数・形・位置の一貫性、ラベル文字の正確さが不安定（要件2・5に抵触しやすい） | 荷物・順序・カメラ・ラベルを完全に制御でき、再現できる |
| 見やすさ | 写実的で見栄えはよい | 簡素だが、状態変化を明瞭に見せやすい |
| 権利・規約 | サービスごとの利用規約の確認が必要 | 自作アセットなら問題が小さい |
| 注意点 | 生成ごとに結果が変わり、正解データと対応させにくい | シミュレータと見た目が同じだと「自作自演」に見える。画風・視点・作業者表現を変えて区別する |

**推奨：プログラムによる3D生成を第一候補とし、短い試作で決める。** 理由は要件1〜5を確実に満たせるため。ツールは見た目をシミュレータと分けやすいBlender（Python・Eevee）を第一候補、導入できない場合はThree.jsの描画を録画する方式を代替とする。動画生成AIは、導入用の雰囲気映像の補助など、解析対象外の用途に限って検討する。

## 説明の入力方式（決定：テキスト入力）

時刻付きの説明テキストを「提供された説明テキスト」として入力する。録音・音声合成は文字起こしが必要になるため、アプリ入力には使わない。提出動画で声を聞かせる場合のみ、同じ文面の録音または音声合成を重ねる（合成エンジンを使う場合は利用条件・クレジット表記を確認する）。

## 入力動画の台本

固定カメラ・斜め上。左に荷物の仮置き場、右にカゴ車（前面開口）。荷物は4個で、識別しやすいタグを付ける。説明文の細部は制作中に調整してよいが、場面構成は以下で確定とする。

| 荷物 | 見た目 | 根拠の与え方 |
|---|---|---|
| A | 底面が広く、軽い硬い箱 | 寸法：模擬荷物マスタ |
| B | 小さいが重い硬い箱 | 重量：模擬荷物マスタ |
| C | ソフトバッグ | 材質：見た目と説明 |
| D | 「ワレモノ」ラベル付きソフトバッグ | 壊れ物：ラベルと説明 |

| 場面 | 動作 | 説明（案） |
|---|---|---|
| 1 | 全体を映す（積付先は空） | 「これから4個を積みます」 |
| 2 | Aを下段に置く | 「硬い箱から先に積みます。底面が0.15平方メートル以上の大きい箱は下に置きます」 |
| 3 | Bを下段に置く | 「この箱は小さいけど重いので、これも下に置きます」（「重い」の基準は示さない） |
| 4 | Cを箱の上に置く | 「柔らかいバッグは後で、上に載せます」 |
| 5 | Dのラベルを確認し、押し込まずに一番上へそっと置く | 「ワレモノなので押し込みません」 |
| 6 | 完成状態を映す | — |

- A（底面0.20㎡）は説明テキストで定義済みの「大きい箱」条件により、ロボットも下段へ置く。
- B（底面0.075㎡、重い）は「重い」の基準が示されていないため要確認の条件となる。ロボットの実行では`on_unknown`から**動画どおり下段へ置く暫定動作**で完了し、「重い」の基準を確認事項に残す。動画の人間の動作を確定ルールにはしない（`docs/WORKFLOW_SPEC.md`「暫定動作」）。
- **属性不明のケースは動画に含めない。** 未実演の分岐として、確認・人への引継ぎ（`on_unknown`）で扱い、観測済みとして表示しない。
- 場面5に対応するロボット側の経路は「押し込まずに上段へ置く」（`docs/ACCEPTANCE.md` A06）。
