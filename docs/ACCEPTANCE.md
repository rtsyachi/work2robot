# 受入基準・検証記録

**完成はファイルが存在することではなく、繰り返し実行できる結果で判断する。** 本ファイルには受入条件を記す。実際の検証結果は日付・コマンド・成功/失敗を追記する。

## 必須の受入条件

| ID | 完成条件 | 実証方法 |
|---|---|---|
| A01 | 作業動画（映像と音声）から、動作・判断分岐・業務の規則を含む構造化案が出る | 動画の観測テキストと音声の文字起こしを使い、Claude API応答を保存して評価用正解データと比較・目視確認。固定テキストでの抽出成功は部分達成とする |
| A02 | 映像・発話・提供テキスト・模擬データ・推測・未確認を区別。分岐ノードや規則を選ぶと根拠の動画区間・発話が表示される | 出力の根拠表示と、選択時の表示を確認 |
| A03 | 説明に数値がない基準は推測で決めず確認事項に残り、確定した分岐・合否判定として扱わない。説明やカゴ車の表示にある数値（積載上限150kgなど）は根拠付きで使い、Claudeが閾値を生成しない | 要確認の条件・重心のずれの合否が「未定義」になることと、閾値の根拠表示を確認 |
| A04 | 生成したワークフロー・業務の規則を**同じ実行器**へ渡せる | 検証器と業務実行器での実行を確認 |
| A05 | 硬い箱と柔らかいバッグで異なる経路・置き方になる（柔らかいバッグは最後に一番上、上積み厳禁） | シナリオv2の業務実行トレースを確認（`app/tests/test_job_rules.py`） |
| A06 | 抽出した業務の規則が実行結果に反映される：重い順に下から、レンガ積み（同じ段で縦横の組み合わせ）、偏荷重の回避、底面の全面支持、上積み厳禁、積載重量・高さ・はみ出しの確認 | 規則ごとの`rule_results`と配置を確認。規則を外すと結果が変わることをテストで確認 |
| A07 | 不明属性・要確認の条件では不明経路を通り、暫定動作（動画どおり、またはAIの仮説と明示）で完了し、確認事項を残す。実行器が扱えない規則・条件が合わず適用しなかった規則は「未対応」「未適用」と表示し、適用済みに見せない | 別の荷物条件（`alt_batch`）と未対応の規則を含む業務定義で確認 |
| A08 | グラフのハイライトと3D動作がトレースに連動 | 動画・スクリーンキャプチャによる確認 |
| A09 | 仮想検証の結果、確認事項（未定義の条件・不足情報）、実機の未検証事項を分けて示す | 事前チェック画面を確認 |
| A10 | 3分以内の日本語動画で一連の動作が見える | 通し録画で確認 |
| A11 | 公開GitHubに秘密情報・流用禁止データ・未許諾素材がない | `git status`、ファイル確認、起動手順確認、導入用実写素材の利用条件記録 |
| A12 | 動画生成用の台本・人の配置・正解データがアプリの入力経路に入っていない。模擬素材であることが画面に表示される | 入力経路のコード確認、画面確認 |
| A13 | 15〜20個の荷物を扱う一連の自然なカゴ車積付動画で、作業者の説明と映像上の行動が対応している | 入力動画（元動画・短縮版）を目視確認、観測テキストと文字起こしの時刻を照合 |
| A14 | 業務から能力要件（数値はコードで計算）が出て、Claudeが**模擬の部品一覧の中から**構成を選定理由・候補外・未確認の点つきで仮選定する。仕様照合は決定的なコードで行い、未確認の能力は未確認のまま残る | `app/tests/test_hardware*.py`、`app/scripts/run_hardware_selection.py` の保存結果、画面の③ロボット構成 |
| A15 | 選んだ構成が業務実行に反映される：能力が足りない荷物は持ち上げずに人へ引き継ぎ、届かない位置には置かない。構成を替えると結果が変わる | `app/tests/test_hardware.py`・`app/tests/test_api_v2.py`、画面で推薦構成と比較用の構成を実行 |
| A17 | 荷物マスタ・環境マスタ（カゴ車・仮置き場）を最初に登録でき、決定的に検証される（エラーは保存しない）。登録した値が能力照合・業務実行に反映され、初期値に戻せる | `app/tests/test_masters.py`・`app/tests/test_api_v2.py`、画面の⓪マスタ登録 |
| A16 | 改善余地は仮説として表示され、確認事項（曖昧な規則・不足情報・未確認の能力・実機PoC）と分けて示される。実証済みの表現がない | 画面の⑤導入前評価 |

## データ整合性の検証と実演は別
