# 実装方針・モジュール境界

**この文書は提案アーキテクチャ。実装完了を意味しない。**

## 全体フロー

```text
[データ確認（Step 1）] マスタ（商品マスタ・環境マスタ＝カゴ車・仮置き場・作業エリア）＋トランザクション（出荷予定・出荷実績）→ 決定的な検証・動画との対応確認 → 登録
   ↓ （以降の全工程が登録したマスタを前提にする）
入力（模擬作業動画＋作業者の説明音声）＋ 商品マスタ・環境マスタ・出荷予定
   ↓
[文字起こし（ローカルWhisper）] ＋ [観測（Claude・画像入力）] → 時刻付きの発話 S… と観測 O…
   ↓
[Claude抽出] → 業務の規則（Level 1）・荷物1個のワークフロー（Level 2）・根拠・確認事項
   ↓
[検証器] → 検証済みのワークフロー・業務定義
   ↓
[能力要件の計算（決定的）] → 可搬重量・大きさ・リーチ・必要な能力
   ↓ ＋ 模擬の部品一覧
[Claudeによる構成の仮選定] → 構成・選定理由・候補外・未確認の点・改善の仮説
   ↓
[仕様照合（決定的）] → ok／ng／未確認
   ↓
[業務実行器（決定的）] ← 構成の能力プロファイル（扱えない荷物は持ち上げない・届かない位置に置かない）
   ↓
業務実行トレース（判断・配置・基本動作・能力の判定）
   ├→ [グラフ表示]：Level 1・Level 2のハイライト、根拠の表示
   ├→ [3Dビュー]：選んだ構成のロボットの動作（トレースの再生）
   └→ [シミュレーション評価]：照合結果・改善余地（仮説）・不足情報・実機PoC項目・人の確認
```

### シナリオを中心としたデータの紐づけ（2026-11-06）

シナリオ＝「カゴ車への混載荷物積付」のような**業務単位**。作業動画と出荷予定はシナリオに紐づくデータで、IDには含めない（動画を変えても、別の出荷で検証しても同じシナリオ）。今回は1シナリオ・1動画。新しいIDは `scenario_id` と `execution_id` だけで、ほかは既存のファイル名を流用する（`app/backend/scenario.py`）。

| キー | 実体 | 保存先 |
|---|---|---|
| `scenario_id` | `sc_cage_cart_loading`（業務の種類 `cage_cart_loading`・名前・対象の出荷予定 `batch_id`） | `local_media/scenario.json`（なければ既定） |
| `video_id` | 作業動画のファイル名（今の動画は `inputs.current_video()`） | `local_media/uploads/` |
| `workflow_id` | 抽出の版のファイル名（`extraction_日時.json`。直した版は `meta.revision.of` で前の版につながる） | `local_media/extractions/` |
| `robot_config_id` | 保存した構成は `robot_日時_名前`、Claudeの仮選定は `hardware_日時`（やり直すと別ID）。構成は `basis`＝選定時の `scenario_id`・`workflow_id`・`batch_id`・照合の件数を持つ | `local_media/robot_configs/`・`hardware_selections/` |
| `execution_id` | `exec_日時`。`scenario_id`・`video_id`・`workflow_id`・`robot_config_id`・`batch_id` を参照し、実行結果（`/api/v2/run` の応答）を含む | `local_media/executions/` |

- **業務要件はシナリオの対象の出荷予定から導く**（`/api/v2/check`・`/api/v2/run` の `batch_id`）。Step 4 の照合と Step 5 の判定は同じ要件・同じ照合（`check_config`）で、Step 4 で分かる能力不足は Step 4 で示す。Step 5 は引継ぎを「Step 4 の照合で判明済み（能力不足）」と「実行して判明（置き場所・積載上限など）」に分ける。
- Step 5 の構成一覧では、保存時と今のワークフローの版・出荷予定が違えば「今の要件で照合し直した」と示す。
- Step 6 は保存した実行結果（`GET /api/v2/executions/latest`）を参照し、評価の根拠（ワークフローの版・構成・出荷予定・実行ID）を表示する。
- 画面上部に対象のシナリオを表示し、出荷予定を変えると `PUT /api/v2/scenario` でシナリオに記録する。

### 検証器（`app/backend/workflow/validator.py`）

ワークフローJSONが**実行してよい形になっているか**を、決定的なコードで判定する。Claudeが作った案も手書きの案も、必ず同じ検証器を通す。

- **構造：** 必須キー（`workflow_id`, `version`, `start_node_id`, `nodes`）、ノード型ごとの必須フィールド、ノードIDの一意性。
- **参照：** `start_node_id` と全ての遷移先（`next`, `on_true`, `on_false`, `on_unknown`）が存在する。
- **グラフ：** 循環がない。開始ノードから全ノードに到達でき、全ての経路が `end` に到達する。
- **分岐：** 全ての `decision` に `on_unknown` がある。演算子がホワイトリスト内。`definition_status` があり、`defined` の閾値には根拠がある。`needs_confirmation` の閾値を推測値で埋めていない。
- **スキル：** `skill_name` がスキル一覧に存在し、`parameters` がその定義に合う。
- **出力：** エラーが1つでもあれば実行器に渡さない。警告は表示用に返す。
- **しないこと：** 「この分岐は業務上正しいか」の判断や、エラー箇所の自動補完。

### 実行器（`app/backend/workflow/executor.py`）

検証済みワークフローと**荷物1個の属性**から、通る経路を決めて実行トレースを出す。同じワークフロー版・入力・スキル一覧なら、常に同じトレースを返す。

- **進み方：** `start_node_id` から1ノードずつ遷移する。
  - `observe`：必要な属性の有無と出所を記録する。欠けている属性は「不明」として保持し、補完しない。
  - `decision`：ホワイトリスト演算子による3値（真・偽・不明）判定。`needs_confirmation` の分岐は常に「不明」として `on_unknown` へ進み、理由を記録する。
  - `skill`：模擬ロボットへの動作指示（スキルイベント）を記録する。暫定動作なら理由と根拠も記録する。実際の動作や物理計算はしない。
  - `handoff`：人への確認・引継ぎの理由を記録する。
  - `end`：処理結果を確定する。
- **出力（実行トレース）：** 通過したノードと辺、各判定で使った属性値と出所、判定結果、スキルイベント、暫定動作、引継ぎ理由、最終結果。
- **安全策：** 検証に通っていないワークフローは実行しない。ケースIDや荷物IDで分岐をハードコードしない。
- **しないこと：** Claudeの呼び出し、描画、複数荷物の順序決め（バッチの扱いは実行器の外。詳細は未確定）。

## 画面の構成（6ステップ、2026-11-04〜。表示の番号は1始まり：1 データ確認・2 シナリオ作成・3 ワークフロー確認・4 ロボット構成・5 シミュレーション実行・6 シミュレーション評価。内部の `step` は 0〜5 のまま）

バックエンドは1つのまま、画面だけを工程ごとに分ける（`app/frontend/src/App.tsx` が状態を持ち、`app/frontend/src/steps/` の各画面へ渡す）。工程の移動は左のメニュー（`StepNav`。番号と名称だけで状態は出さない）で行う。メニューは初期からピン止め（左に常に表示）で、上部にロゴ（`app/frontend/public/work2robot_logo.png`、`materials/work2robot.png` の余白を切ったもの）と三本線、下部にピンのボタンを置く。ピンを外すと引き出しになり（外した設定はブラウザに覚える）、上部のバーの三本線で開く。画面ごとの説明文と「次へ」は置かない。上部のバーには現在の工程と、Step 3 以降は対象のシナリオを表示する（出荷予定の選択は上部に置かず、Step 2 のトランザクション登録で選ぶ）。

| ステップ | 画面 | 使うデータ |
|---|---|---|
| ① データ確認 | `MasterStep` | 開くと商品マスタを表示する（全体の概要画面は置かない）。左は3区分（マスタ：商品マスタ・カゴ車マスタ／トランザクション：出荷予定・出荷実績／その他：倉庫内マップ）とデータ名だけ。右の各データ画面は、上部にタイトルと件数・注意の件数、目的（1行）を出し、その下に操作の行（追加・修正・削除・保存）、1列目に行番号（No.）を付けたテーブルの一覧と、選んだ1件の詳細（「修正」で入力欄になる）／倉庫内マップ。保存の結果は一覧の上に出す。確認事項の一覧は上部の検証結果のボタンから開く。解析結果が別の動画から作られていれば Step 1〜6 の上部に警告。ツリー・列・入力欄は API が返すマスタの定義（`definitions`＝`MASTER_DEFS`）から作る。ファイルの取り込みは置かない（一括登録はSEが外部で行う）。入力中の検証（`POST /api/v2/masters/validate`）、登録（`PUT /api/v2/masters`、エラーがあれば422）。初期値に戻す API（`DELETE`）は残すが画面にボタンは置かない。動画の観測に出てくる荷物IDとの照合も表示。登録すると状態を取り直し、③〜⑤の結果を破棄する |
| ② シナリオ作成 | `AnalysisStep` | 左にシナリオ（`scenario`）・マスタとトランザクション（`masters.definitions` の区分から件数と紐づけの状態）・作業動画（`inputs.video`）・ワークフロー生成の状態（`extraction`・`inputs.job`。生成は `POST /api/v2/analyze`）、右に作業動画のプレビュー。タスク構造（大タスク・小タスク）は Step 2 では表示しない（データと `lib/taskSync.ts` は残す） |
| ③ ワークフロー確認 | `WorkflowStep`（`Level1Graph`＋`WorkflowGraph`＋`NodeDetail`） | 抽出したワークフロー・業務の規則、**能力の制約なしの実行**（`POST /api/v2/run` で `config_id: null`）の荷物別トレース |
| ④ ロボット構成 | `HardwareStep`（`RobotFigure`） | 仮想メーカーのカタログ（機種＋オプション）、能力要件、Claudeの仮選定、`POST /api/v2/check`（構成＝`product_id`＋オプション）の照合 |
| ⑤ シミュレーション実行 | `ExecutionStep`（`Robot3D`＋`WorkflowGraph`） | 選んだ構成での実行（`POST /api/v2/run`）の業務実行トレース。3Dは Step 4 と同じ製品モデルを関節で動かし（移動式は台車ごと走行、ヒューマノイドは決定的な歩行のタイムラインで足を接地させて歩き・旋回し、肘を下に曲げて両腕で抱える、固定式は台座から動かない）、基本動作を接近・把持・持ち上げ・搬送・減速して下ろす・解除・退避に分けて再生する（`lib/robotTimeline.ts`）。業務全体は5工程の進捗に要約し、詳細なLevel 1は③に任せる |
| ⑥ シミュレーション評価 | `EvaluationStep` | 同じ実行の事前評価・照合、同じ荷物の条件で実行済みの構成の比較 |

- **定義と実行の分離：** Level 2のワークフロー定義は1つ。荷物ごとの経路は実行トレース（`items[].item_trace`）から強調するだけ。
- **整合性：** 実行結果は「構成＋荷物の条件」の組ごとに保持する。構成や条件を変えると、その組の④・⑤は未実行（他の組の結果があれば「再実行が必要」）になり、古い結果を表示しない。
- **人間との比較：** 観測テキストのタグ（`objects`）から、同じ荷物を扱う動画区間を特定して表示する。特定できない荷物は動画を同期しない。
- すべての動き・ハイライトは同じ業務実行トレースから作り、画面用の別の実行ロジックは持たない。

## 推奨するシンプルな技術構成

- **Frontend:** React / TypeScript / React Three Fiber（Three.js）。動画・フロー・仮想ロボット・事前チェックを同じワークスペースに表示。
- **Backend:** Python / FastAPI。Claude API呼び出し、ワークフローの検証・実行、トレース発行。
- **AI:** Claude API。動画の選択フレームや説明（発話または提供テキスト）の意味解析、分岐案、曖昧な条件・不足情報の整理。実装前に利用モデルの画像入力仕様を調べる。
- **Workflow:** Pythonで決定的に評価。ロボットの状態更新と分岐判定をClaudeの文章生成と切り離す。データ形式は `docs/WORKFLOW_SPEC.md` を参照。
- **Sim:** 軽量な模擬動作。把持や接触の物理精度は主張しない。

## API境界の案（確定前の提案）

| API | 主な役割 |
|---|---|
| `POST /api/observe` | 動画フレームから時刻付きの観測テキストを生成（後から実装） |
| `POST /api/extract` | 観測テキスト・説明テキスト・属性定義からワークフローと確認事項を生成（入力はテキストのみ。実装済み、課金あり。結果は `local_media/extractions/` に保存） |
| `GET /api/extract/latest` | 保存済みの最新の抽出結果を返す（再生成しない。実装済み） |
| `GET /api/demo/inputs` | 抽出の入力テキスト（説明・開発用観測・属性定義）を返す（実装済み） |
| `GET /api/demo/fixtures` | 手書きワークフロー・スキル一覧・模擬荷物を返す（実装済み） |
| `POST /api/workflows/validate` | グラフ構造と分岐の整合性を検証（実装済み） |
| `POST /api/workflows/run` | グラフ＋荷物1個から実行トレースを生成（実装済み。検証エラーは422） |
| `GET /api/v2/state` | v2の画面の初期表示：保存済みの文字起こし・観測・抽出・仮選定、能力要件、比較用の構成、マスタ（実装済み） |
| `GET・PUT・DELETE /api/v2/masters`、`POST /api/v2/masters/validate` | マスタと出荷予定の取得・登録（検証エラーは422で保存しない）・初期値に戻す・検証のみ。定義（区分・登録する人・登録方法を含む）も返す（実装済み） |
| `GET /api/v2/inputs` | 作業動画の情報（ファイル・長さ・解像度・音声の有無）と、解析結果ごとの元の動画・今の動画との対応（`backend/inputs.py`）（実装済み。`/api/v2/state` の `inputs` にも含む） |
| `POST /api/v2/run` | 構成（`config_id`）と荷物のまとまりで業務を実行し、仕様照合とシミュレーション評価を返す（実装済み） |
| `GET /api/media/input_video.mp4` | 今の作業動画（アップロードした動画、なければ `materials/input_video_v5.mp4`）（実装済み） |
| `POST /api/v2/video?name=…`／`DELETE /api/v2/video` | Step 2：動画（mp4のバイト列そのまま）を `local_media/uploads/upload_日時.mp4` に保存して今の動画にする（読めない・音声なし・10分超は 422 で保存しない）／v5デモに戻す（アップロード済みの動画と結果は消さない）（実装済み） |
| `POST /api/v2/workflow/edit` | Step 3 の直接編集（`{"ops": [...], "reason": 根拠}`）。検証に通れば新しい版として保存、通らなければ 422（実装済み） |
| `POST /api/v2/workflow/propose`／`POST /api/v2/workflow/proposals/{id}/apply`／`DELETE …/{id}` | Claudeへの修正指示から修正案と差分を作る（課金あり・保存しない）／承認して新しい版として保存（作成後に版が変わっていれば 422）／破棄（実装済み） |
| `POST /api/v2/workflow/revert` | 1つ前の版に戻す（今の版も残す）（実装済み） |
| `POST /api/v2/hardware/reselect` | Step 4：今のワークフローの版でClaudeの仮選定をやり直す（課金あり。状態は `GET /api/v2/analyze`）。`/api/v2/state` の `selection_stale` が古い仮選定を示す（実装済み） |
| `POST /api/v2/analyze`／`GET /api/v2/analyze` | Step 2「解析開始」（`{"supplement": 任意の補足}`。課金あり・同時に1件）／その状態（実装済み） |

**注意：** 手書きのデモ入力データは初期プロトタイピング用。動画からの抽出結果と差し替えても同じ検証・実行経路を通す。結果の捏造やシナリオ固有のハードコードはしない。

## 開発順（縦スライス）

1. **一連の最小成功パス：** 手書きのワークフローを検証・実行し、通常荷物と例外荷物で違うトレースを生成。自動テストを通す。
2. **実行イベントと3Dビューの接続：** トレースからノード・辺をハイライト、箱移動と人への引継ぎを可視化。
3. **Claude抽出の接続（テキスト入力）：** 固定の観測テキスト・説明テキストから出した構造化案を同じ検証器へ通す。未定義の条件・不足情報を確認事項として出力。
4. **自動化事前チェック：** トレースとモックの能力定義から、計画上の結果と実機検証項目を表示。
4b. **動画→観測テキスト変換：** 入力動画から観測テキストを生成し、手順3の固定テキストと差し替えても同じ抽出経路を通す。
5. **動画の通し収録：** `docs/DEMO.md` と照合して操作を確認し、3分以内に編集。

**入力素材の制作（並行トラック）：** `docs/DEMO_INPUT.md` のM1〜M6。手順1〜4は素材なしで進める。手順4bはM2の試作動画で着手でき、本番素材（M3〜M5）で仕上げる。手順5はM3〜M6と4bの完了が前提。ユーザーの撮影待ちは依存関係に含めない。

## 複数エージェント利用

境界とデータ契約が決まった後なら、**Claude抽出・UI/3D・テスト/レビュー**を独立作業として並列化できる。初期段階から常時複数エージェントを立てず、共通ファイル編集・統合が増える場面はLead 1体で進める。Agent Teamsは実験的機能で、使用可否・費用は実環境で確認する。並列開発の有無は成果物の価値より優先しない。
