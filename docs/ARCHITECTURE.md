# 実装方針・モジュール境界

**この文書は提案アーキテクチャ。実装完了を意味しない。**

## 全体フロー

```text
[マスタ登録（Step 0）] 荷物マスタ（属性・便）・環境マスタ（カゴ車・仮置き場・作業エリア）→ 決定的な検証 → 登録
   ↓ （以降の全工程が登録したマスタを前提にする）
入力（模擬作業動画＋作業者の説明音声）＋ 荷物マスタ・環境マスタ
   ↓
[文字起こし（ローカルWhisper）] ＋ [観測（Claude・画像入力）] → 時刻付きの発話 S… と観測 O…
   ↓
[Claude抽出] → 業務の規則（Level 1）・荷物1個のワークフロー（Level 2）・根拠・確認事項
   ↓
[検証器] → 検証済みのワークフロー・業務定義
   ↓
[能力要件の計算（決定的）] → 可搬重量・大きさ・リーチ・必要な能力
   ↓ ＋ 模擬の部品一覧
[Claudeによる構成の仮選定] → 構成・選定理由・候補外・未確認の点・改善の仮説
   ↓
[仕様照合（決定的）] → ok／ng／未確認
   ↓
[業務実行器（決定的）] ← 構成の能力プロファイル（扱えない荷物は持ち上げない・届かない位置に置かない）
   ↓
業務実行トレース（判断・配置・基本動作・能力の判定）
   ├→ [グラフ表示]：Level 1・Level 2のハイライト、根拠の表示
   ├→ [3Dビュー]：選んだ構成のロボットの動作（トレースの再生）
   └→ [導入前評価]：照合結果・改善余地（仮説）・不足情報・実機PoC項目・人の確認
```

## モジュールの責務

| モジュール | 入力 | 出力 | 担当しないこと |
|---|---|---|---|
| マスタ（`app/backend/workflow/masters.py`） | 荷物マスタ・環境マスタ（初期値 `app/data/masters/`、登録値 `local_media/masters/`） | 検証結果、実行器への荷物の属性・便、業務定義のカゴ車・仮置き場 | 動画からの属性の推定、Claude呼び出し |
| 観測 | 入力動画 | 時刻付きの観測テキスト | 重量・中身など見えない属性の確定 |
| 抽出（Claude） | 観測テキスト・説明テキスト・模擬荷物マスタ | ワークフロー案JSON・確認事項リスト | 分岐の判定・実行 |
| **検証器** | ワークフローJSON・スキル一覧 | 検証結果（合否・エラー・警告） | 内容の業務的な正しさの判断、自動修正 |
| **実行器** | 検証済みワークフロー・荷物1個の属性・スキル一覧 | 実行トレース | Claude呼び出し、物理計算、描画、荷物の順序決め |
| 能力要件・仕様照合（`app/backend/workflow/hardware.py`） | 業務定義・ワークフロー・模擬荷物マスタ・部品一覧・構成 | 能力要件、照合結果（ok／ng／未確認）、能力プロファイル | Claude呼び出し、実機の能力の保証 |
| 構成の仮選定（Claude、`app/backend/ai/hardware_selection.py`） | 抽出済みの業務・能力要件・部品一覧 | 構成・選定理由・候補外・未確認の点・改善の仮説 | 数値の要件の作成、一覧にない部品の提案、照合 |
| グラフ表示・3Dビュー | ワークフロー・実行トレース | 画面表示 | 分岐の判定（トレースを再生するだけ） |
| 導入前評価（`app/backend/workflow/readiness.py`） | ワークフロー・確認事項・実行トレース・スキル一覧・照合結果 | 状態区分ごとの一覧、改善余地（仮説） | 「自動化可能率」などの単一指標、改善効果の断定 |

データ形式（ワークフロー・実行トレース・スキル一覧）の正本は `docs/WORKFLOW_SPEC.md`。

### 検証器（`app/backend/workflow/validator.py`）

ワークフローJSONが**実行してよい形になっているか**を、決定的なコードで判定する。Claudeが作った案も手書きの案も、必ず同じ検証器を通す。

- **構造：** 必須キー（`workflow_id`, `version`, `start_node_id`, `nodes`）、ノード型ごとの必須フィールド、ノードIDの一意性。
- **参照：** `start_node_id` と全ての遷移先（`next`, `on_true`, `on_false`, `on_unknown`）が存在する。
- **グラフ：** 循環がない。開始ノードから全ノードに到達でき、全ての経路が `end` に到達する。
- **分岐：** 全ての `decision` に `on_unknown` がある。演算子がホワイトリスト内。`definition_status` があり、`defined` の閾値には根拠がある。`needs_confirmation` の閾値を推測値で埋めていない。
- **スキル：** `skill_name` がスキル一覧に存在し、`parameters` がその定義に合う。
- **出力：** エラーが1つでもあれば実行器に渡さない。警告は表示用に返す。
- **しないこと：** 「この分岐は業務上正しいか」の判断や、エラー箇所の自動補完。

### 実行器（`app/backend/workflow/executor.py`）

検証済みワークフローと**荷物1個の属性**から、通る経路を決めて実行トレースを出す。同じワークフロー版・入力・スキル一覧なら、常に同じトレースを返す。

- **進み方：** `start_node_id` から1ノードずつ遷移する。
  - `observe`：必要な属性の有無と出所を記録する。欠けている属性は「不明」として保持し、補完しない。
  - `decision`：ホワイトリスト演算子による3値（真・偽・不明）判定。`needs_confirmation` の分岐は常に「不明」として `on_unknown` へ進み、理由を記録する。
  - `skill`：模擬ロボットへの動作指示（スキルイベント）を記録する。暫定動作なら理由と根拠も記録する。実際の動作や物理計算はしない。
  - `handoff`：人への確認・引継ぎの理由を記録する。
  - `end`：処理結果を確定する。
- **出力（実行トレース）：** 通過したノードと辺、各判定で使った属性値と出所、判定結果、スキルイベント、暫定動作、引継ぎ理由、最終結果。
- **安全策：** 検証に通っていないワークフローは実行しない。ケースIDや荷物IDで分岐をハードコードしない。
- **しないこと：** Claudeの呼び出し、描画、複数荷物の順序決め（バッチの扱いは実行器の外。詳細は未確定）。

## 画面の構成（Step 0＋5ステップ、2026-11-04〜）

バックエンドは1つのまま、画面だけを工程ごとに分ける（`app/frontend/src/App.tsx` が状態を持ち、`app/frontend/src/steps/` の各画面へ渡す）。工程の移動は、左上の三本線で開く左のメニュー（`StepNav`、各工程の状態つき。ピン止めすると左に常に表示し、ブラウザに設定を覚える）と、各画面の「次へ」で行う。上部にはロゴ（`app/frontend/public/work2robot_logo.png`、`materials/work2robot.png` の余白を切ったもの）と現在の工程を表示する。

| ステップ | 画面 | 使うデータ |
|---|---|---|
| ⓪ マスタ登録 | `MasterStep` | 荷物マスタ・便・環境マスタの表と配置図、入力中の検証（`POST /api/v2/masters/validate`）、登録（`PUT /api/v2/masters`、エラーがあれば422）、初期値に戻す（`DELETE`）。動画の観測に出てくる荷物IDとの照合も表示。登録すると状態を取り直し、③〜⑤の結果を破棄する |
| ① 作業動画解析 | `AnalysisStep` | 保存済みのタスク構造（大タスク・小タスク・判断条件。`docs/WORKFLOW_SPEC.md`「作業動画のタスク構造」）と文字起こし・観測（`GET /api/v2/state`）。再生位置で表示を切り替える（`lib/taskSync.ts`） |
| ② ワークフロー生成・確認 | `WorkflowStep`（`Level1Graph`＋`WorkflowGraph`＋`NodeDetail`） | 抽出したワークフロー・業務の規則、**能力の制約なしの実行**（`POST /api/v2/run` で `config_id: null`）の荷物別トレース |
| ③ ロボット構成の仮選定 | `HardwareStep`（`RobotFigure`） | 仮想メーカーのカタログ（機種＋オプション）、能力要件、Claudeの仮選定、`POST /api/v2/check`（構成＝`product_id`＋オプション）の照合 |
| ④ 仮想ロボット実行 | `ExecutionStep`（`Robot3D`＋`WorkflowGraph`） | 選んだ構成での実行（`POST /api/v2/run`）の業務実行トレース。3Dは Step 3 と同じ製品モデルを関節で動かし（移動式は台車ごと走行、固定式はコンベヤから受け取る、概念プレビューの機種は動作を描かない）、基本動作を接近・把持・持ち上げ・搬送・減速して下ろす・解除・退避に分けて再生する（`lib/robotTimeline.ts`）。業務全体は5工程の進捗に要約し、詳細なLevel 1は②に任せる |
| ⑤ 導入前評価 | `EvaluationStep` | 同じ実行の事前評価・照合、同じ荷物の条件で実行済みの構成の比較 |

- **定義と実行の分離：** Level 2のワークフロー定義は1つ。荷物ごとの経路は実行トレース（`items[].item_trace`）から強調するだけ。
- **整合性：** 実行結果は「構成＋荷物の条件」の組ごとに保持する。構成や条件を変えると、その組の④・⑤は未実行（他の組の結果があれば「再実行が必要」）になり、古い結果を表示しない。
- **人間との比較：** 観測テキストのタグ（`objects`）から、同じ荷物を扱う動画区間を特定して表示する。特定できない荷物は動画を同期しない。
- すべての動き・ハイライトは同じ業務実行トレースから作り、画面用の別の実行ロジックは持たない。

## 推奨するシンプルな技術構成

- **Frontend:** React / TypeScript / React Three Fiber（Three.js）。動画・フロー・仮想ロボット・事前チェックを同じワークスペースに表示。
- **Backend:** Python / FastAPI。Claude API呼び出し、ワークフローの検証・実行、トレース発行。
- **AI:** Claude API。動画の選択フレームや説明（発話または提供テキスト）の意味解析、分岐案、曖昧な条件・不足情報の整理。実装前に利用モデルの画像入力仕様を調べる。
- **Workflow:** Pythonで決定的に評価。ロボットの状態更新と分岐判定をClaudeの文章生成と切り離す。データ形式は `docs/WORKFLOW_SPEC.md` を参照。
- **Sim:** 軽量な模擬動作。把持や接触の物理精度は主張しない。

## 開発順（縦スライス）

1. **一連の最小成功パス：** 手書きのワークフローを検証・実行し、通常荷物と例外荷物で違うトレースを生成。自動テストを通す。
2. **実行イベントと3Dビューの接続：** トレースからノード・辺をハイライト、箱移動と人への引継ぎを可視化。
3. **Claude抽出の接続（テキスト入力）：** 固定の観測テキスト・説明テキストから出した構造化案を同じ検証器へ通す。未定義の条件・不足情報を確認事項として出力。
4. **自動化事前チェック：** トレースとモックの能力定義から、計画上の結果と実機検証項目を表示。
4b. **動画→観測テキスト変換：** 入力動画から観測テキストを生成し、手順3の固定テキストと差し替えても同じ抽出経路を通す。
5. **動画の通し収録：** `docs/DEMO.md` と照合して操作を確認し、3分以内に編集。

**入力素材の制作（並行トラック）：** `docs/DEMO_INPUT.md` のM1〜M6。手順1〜4は素材なしで進める。手順4bはM2の試作動画で着手でき、本番素材（M3〜M5）で仕上げる。手順5はM3〜M6と4bの完了が前提。ユーザーの撮影待ちは依存関係に含めない。

## 複数エージェント利用

境界とデータ契約が決まった後なら、**Claude抽出・UI/3D・テスト/レビュー**を独立作業として並列化できる。初期段階から常時複数エージェントを立てず、共通ファイル編集・統合が増える場面はLead 1体で進める。Agent Teamsは実験的機能で、使用可否・費用は実環境で確認する。並列開発の有無は成果物の価値より優先しない。
