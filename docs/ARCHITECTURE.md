# 実装方針・モジュール境界

**この文書は提案アーキテクチャ。実装完了を意味しない。**

## 全体フロー

```text
入力（デモ用模擬作業動画・説明テキスト・模擬荷物マスタ）
   ↓
[観測：動画→観測テキスト] → 時刻付きの観測可能な動作・状態変化（後から実装。それまでは開発用の固定テキスト）
   ↓ 観測テキスト ＋ 説明テキスト ＋ 模擬荷物マスタ
[Claude抽出] → 作業・判断・根拠・曖昧さを含むJSON案
   ↓
[検証器] → 検証済みの分岐付きワークフロー（＋抽出時の確認事項リスト。回答入力UIはMVP対象外）
   ↓
[決定的ワークフロー実行器] ← 荷物属性・模擬スキル一覧
   ↓
実行トレース・模擬スキルイベント
   ├→ [グラフ表示]：通過したノード・辺のハイライト、根拠の表示
   ├→ [3Dビュー]：仮想ロボットの動作
   └→ [事前チェック]：検証結果・確認事項・実機PoC項目
```

## モジュールの責務

| モジュール | 入力 | 出力 | 担当しないこと |
|---|---|---|---|
| 観測 | 入力動画 | 時刻付きの観測テキスト | 重量・中身など見えない属性の確定 |
| 抽出（Claude） | 観測テキスト・説明テキスト・模擬荷物マスタ | ワークフロー案JSON・確認事項リスト | 分岐の判定・実行 |
| **検証器** | ワークフローJSON・スキル一覧 | 検証結果（合否・エラー・警告） | 内容の業務的な正しさの判断、自動修正 |
| **実行器** | 検証済みワークフロー・荷物1個の属性・スキル一覧 | 実行トレース | Claude呼び出し、物理計算、描画、荷物の順序決め |
| グラフ表示・3Dビュー | ワークフロー・実行トレース | 画面表示 | 分岐の判定（トレースを再生するだけ） |
| 事前チェック | ワークフロー・確認事項・実行トレース・スキル一覧 | 状態区分ごとの一覧 | 「自動化可能率」などの単一指標 |

データ形式（ワークフロー・実行トレース・スキル一覧）の正本は `docs/WORKFLOW_SPEC.md`。

### 検証器（`backend/workflow/validator.py`）

ワークフローJSONが**実行してよい形になっているか**を、決定的なコードで判定する。Claudeが作った案も手書きの案も、必ず同じ検証器を通す。

- **構造：** 必須キー（`workflow_id`, `version`, `start_node_id`, `nodes`）、ノード型ごとの必須フィールド、ノードIDの一意性。
- **参照：** `start_node_id` と全ての遷移先（`next`, `on_true`, `on_false`, `on_unknown`）が存在する。
- **グラフ：** 循環がない。開始ノードから全ノードに到達でき、全ての経路が `end` に到達する。
- **分岐：** 全ての `decision` に `on_unknown` がある。演算子がホワイトリスト内。`definition_status` があり、`defined` の閾値には根拠がある。`needs_confirmation` の閾値を推測値で埋めていない。
- **スキル：** `skill_name` がスキル一覧に存在し、`parameters` がその定義に合う。
- **出力：** エラーが1つでもあれば実行器に渡さない。警告は表示用に返す。
- **しないこと：** 「この分岐は業務上正しいか」の判断や、エラー箇所の自動補完。

### 実行器（`backend/workflow/executor.py`）

検証済みワークフローと**荷物1個の属性**から、通る経路を決めて実行トレースを出す。同じワークフロー版・入力・スキル一覧なら、常に同じトレースを返す。

- **進み方：** `start_node_id` から1ノードずつ遷移する。
  - `observe`：必要な属性の有無と出所を記録する。欠けている属性は「不明」として保持し、補完しない。
  - `decision`：ホワイトリスト演算子による3値（真・偽・不明）判定。`needs_confirmation` の分岐は常に「不明」として `on_unknown` へ進み、理由を記録する。
  - `skill`：模擬ロボットへの動作指示（スキルイベント）を記録する。暫定動作なら理由と根拠も記録する。実際の動作や物理計算はしない。
  - `handoff`：人への確認・引継ぎの理由を記録する。
  - `end`：処理結果を確定する。
- **出力（実行トレース）：** 通過したノードと辺、各判定で使った属性値と出所、判定結果、スキルイベント、暫定動作、引継ぎ理由、最終結果。
- **安全策：** 検証に通っていないワークフローは実行しない。ケースIDや荷物IDで分岐をハードコードしない。
- **しないこと：** Claudeの呼び出し、描画、複数荷物の順序決め（バッチの扱いは実行器の外。詳細は未確定）。

## 推奨するシンプルな技術構成

- **Frontend:** React / TypeScript / React Three Fiber（Three.js）。動画・フロー・仮想ロボット・事前チェックを同じワークスペースに表示。
- **Backend:** Python / FastAPI。Claude API呼び出し、ワークフローの検証・実行、トレース発行。
- **AI:** Claude API。動画の選択フレームや説明（発話または提供テキスト）の意味解析、分岐案、曖昧な条件・不足情報の整理。実装前に利用モデルの画像入力仕様を調べる。
- **Workflow:** Pythonで決定的に評価。ロボットの状態更新と分岐判定をClaudeの文章生成と切り離す。データ形式は `docs/WORKFLOW_SPEC.md` を参照。
- **Sim:** 軽量な模擬動作。把持や接触の物理精度は主張しない。

## API境界の案（確定前の提案）

| API | 主な役割 |
|---|---|
| `POST /api/observe` | 動画フレームから時刻付きの観測テキストを生成（後から実装） |
| `POST /api/extract` | 観測テキスト・説明テキスト・属性定義からワークフローと確認事項を生成（入力はテキストのみ。実装済み、課金あり。結果は `local_media/extractions/` に保存） |
| `GET /api/extract/latest` | 保存済みの最新の抽出結果を返す（再生成しない。実装済み） |
| `GET /api/demo/inputs` | 抽出の入力テキスト（説明・開発用観測・属性定義）を返す（実装済み） |
| `GET /api/demo/fixtures` | 手書きワークフロー・スキル一覧・模擬荷物を返す（実装済み） |
| `POST /api/workflows/validate` | グラフ構造と分岐の整合性を検証（実装済み） |
| `POST /api/workflows/run` | グラフ＋荷物1個から実行トレースを生成（実装済み。検証エラーは422） |
| `POST /api/feasibility` | トレースと模擬能力定義から実機検証事項を整理 |

**注意：** 手書きのデモ入力データは初期プロトタイピング用。動画からの抽出結果と差し替えても同じ検証・実行経路を通す。結果の捏造やシナリオ固有のハードコードはしない。

## 開発順（縦スライス）

1. **一連の最小成功パス：** 手書きのワークフローを検証・実行し、通常荷物と例外荷物で違うトレースを生成。自動テストを通す。
2. **実行イベントと3Dビューの接続：** トレースからノード・辺をハイライト、箱移動と人への引継ぎを可視化。
3. **Claude抽出の接続（テキスト入力）：** 固定の観測テキスト・説明テキストから出した構造化案を同じ検証器へ通す。未定義の条件・不足情報を確認事項として出力。
4. **自動化事前チェック：** トレースとモックの能力定義から、計画上の結果と実機検証項目を表示。
4b. **動画→観測テキスト変換：** 入力動画から観測テキストを生成し、手順3の固定テキストと差し替えても同じ抽出経路を通す。
5. **動画の通し収録：** `docs/DEMO.md` と照合して操作を確認し、3分以内に編集。

**入力素材の制作（並行トラック）：** `docs/DEMO_INPUT.md` のM1〜M6。手順1〜4は素材なしで進める。手順4bはM2の試作動画で着手でき、本番素材（M3〜M5）で仕上げる。手順5はM3〜M6と4bの完了が前提。ユーザーの撮影待ちは依存関係に含めない。

## 複数エージェント利用

境界とデータ契約が決まった後なら、**Claude抽出・UI/3D・テスト/レビュー**を独立作業として並列化できる。初期段階から常時複数エージェントを立てず、共通ファイル編集・統合が増える場面はLead 1体で進める。Agent Teamsは実験的機能で、使用可否・費用は実環境で確認する。並列開発の有無は成果物の価値より優先しない。
